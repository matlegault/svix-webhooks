AutoConfig tokens let your customers register webhook endpoints or subscribe to sinks without calling your API directly.

## Overview of the AutoConfig flow

AutoConfig removes the need for your customers to interact with your Svix API credentials. Instead, you generate a short-lived token scoped to a single application, hand it to the customer, and they use it to register their own endpoint or subscribe to a streaming sink. There are two token formats (needs confirmation):

- **v2 tokens** (prefix `auto_v2_`) — the current format, used to subscribe to a streaming sink via `AutoConfigConsumer`. (needs confirmation)
- **v1 tokens** (prefix `auto_v1_`) — the deprecated format, used to register a webhook endpoint directly. (needs confirmation)

`AutoConfig` and `AutoConfigConsumer` are hand-written helpers available in every official SDK. `AutoConfig` handles the token exchange, and `AutoConfigConsumer` handles the sink subscription. `python/svix/api/`@`124218287bb291261bc7227b1e218be45d59dd9c` (needs confirmation)

## Generating a v2 AutoConfig token

You generate a token server-side using your Svix API credentials. The token is scoped to one application and carries the permissions needed for the consumer to subscribe. Your backend calls the Svix API to create the token, then returns it to your customer's client. (needs confirmation)

The `AutoConfigOut` model is returned by the token-creation endpoint and contains the token string your customer will use. `python/svix/api/`@`124218287bb291261bc7227b1e218be45d59dd9c` (needs confirmation)

A typical server-side flow looks like this:

```python
from svix import Svix, SvixOptions

svix = Svix("YOUR_API_KEY")

# Create or retrieve the application for this customer
app = svix.application.get_or_create({"name": "customer-app", "uid": "customer-123"})

# Generate an AutoConfig token for that application
token_out = svix.authentication.app_portal_access(app.id, {})
# token_out.token is the value you send to your customer
```

Pass the resulting token to your customer's frontend or service. Do not expose your main API key. `python/svix/api/`@`124218287bb291261bc7227b1e218be45d59dd9c` (needs confirmation)

## Embedding the consumer widget or SDK call

Once your customer has the token, they use it to register their endpoint or subscribe to a sink. You can embed this flow in a frontend widget or call it from a backend service using any official SDK. (needs confirmation)

The `AutoConfig` class accepts the token and the target endpoint URL. Here is an example in TypeScript (needs confirmation):

```typescript
import { AutoConfig } from "svix";

const autoConfig = new AutoConfig("auto_v2_YOUR_TOKEN", "https://example.com/webhooks");
await autoConfig.init();
```

And in Go:

```go
import "github.com/svix/svix-webhooks/v2/go"

ac := svix.NewAutoConfig("auto_v2_YOUR_TOKEN", "https://example.com/webhooks")
err := ac.Init(ctx)
```

## AutoConfigConsumer: subscribing to a sink

`AutoConfigConsumer` is used when the customer wants to subscribe to a streaming sink rather than register a webhook endpoint. It takes the token and a sink configuration object. (needs confirmation)

In Go:

```go
import "github.com/svix/svix-webhooks/v2/go"

consumer := svix.NewAutoConfigConsumer("auto_v2_YOUR_TOKEN", sinkIn)
err := consumer.Subscribe(ctx)
```

## Handling v1 (deprecated) tokens

v1 tokens (prefix `auto_v1_`) register a webhook endpoint directly rather than subscribing to a sink. All SDKs still support them for backwards compatibility, but you should issue v2 tokens for new integrations. (needs confirmation)

When `AutoConfig` receives a v1 token it registers an endpoint on behalf of the customer. The behavior is the same from the caller's perspective: pass the token and the target URL to `AutoConfig` and call `init()`. `kotlin/lib/src/main/kotlin/`@`124218287bb291261bc7227b1e218be45d59dd9c` (needs confirmation)

```python
from svix import AutoConfig

# v1 token — still works, but prefer v2
ac = AutoConfig("auto_v1_YOUR_TOKEN", "https://example.com/webhooks")
ac.init()
```

## Revoking tokens

Tokens are short-lived and scoped to a single application. To prevent a token from being used after it is issued, revoke it through the Svix authentication API before it expires. Your server controls token issuance, so you can also limit exposure by generating tokens only immediately before handing them to the customer. `python/svix/api/`@`124218287bb291261bc7227b1e218be45d59dd9c` (needs confirmation)

## Testing the flow end-to-end

To verify your integration works:

1. Generate a v2 AutoConfig token for a test application using your API key. `python/svix/api/`@`124218287bb291261bc7227b1e218be45d59dd9c` (needs confirmation)
2. Pass the token to `AutoConfigConsumer` with a test sink configuration and call `subscribe()`. `go/`@`124218287bb291261bc7227b1e218be45d59dd9c` (needs confirmation)
3. Send a test message to the application and confirm it arrives at the sink. (needs confirmation)
4. Repeat with a v1 token and a real HTTPS endpoint to confirm backwards-compatible behavior. `kotlin/lib/src/main/kotlin/`@`124218287bb291261bc7227b1e218be45d59dd9c` (needs confirmation)

Regional API selection is automatic: the SDK reads the token suffix (`us`, `eu`, `in`, `ca`, `au`) and routes requests to the correct regional endpoint, so you do not need to configure the base URL manually. `javascript/src/api/`@`124218287bb291261bc7227b1e218be45d59dd9c` (needs confirmation)
