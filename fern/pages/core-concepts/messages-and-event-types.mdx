title: "Messages & Event Types"
---

Messages are the webhook payloads Svix delivers to your endpoints, and event types are the labels that categorize them.

## What is a message?

A message is a single webhook payload that Svix delivers to one or more endpoints registered under an application. When you send a message, Svix queues it, attempts delivery to every matching endpoint, and retries on failure. Each message belongs to exactly one application and carries an event type that identifies what happened.

## Message payload structure

You create a message by posting to `POST /api/v1/app/{app_id}/msg`. The request body is the `MessageIn` structure with these fields:

| Field | Required | Description |
|---|---|---|
| `eventType` | Yes | The event type name for this message. |
| `payload` | Yes | A JSON object — must be an object, not an array or scalar. |
| `eventId` | No | Optional unique identifier (idempotency key) for the message. |
| `channels` | No | 1–5 free-form strings that endpoints can filter by. |
| `payloadRetentionPeriod` | No | Days to retain the payload (5–90, default 90). |
| `application` | No | Optionally create the application alongside the message. |

The `payload` field accepts the aliases `data` and `payload` interchangeably, and it must be a JSON object.

A minimal message creation request looks like this:

```json
{
  "eventType": "user.signup",
  "payload": {
    "userId": "user_123",
    "email": "user@example.com"
  }
}
```

Channels let you further segment delivery. An endpoint can subscribe to specific channels, and a message is only delivered to endpoints whose channel filter matches. A message can carry between 1 and 5 channels.

## Event types and schemas

An event type is a named category for messages, such as `user.signup` or `invoice.paid`. Endpoints can filter to receive only specific event types — the filter list must contain at least one item and is validated on creation.

Event types are managed through the `event_type` endpoint module.

When you create an endpoint, you can pass a list of event type names to `filterTypes`. If you leave it empty, the endpoint receives all event types. The server validates that the list is non-empty when provided.

## Idempotency keys

The `eventId` field on a message acts as an idempotency key. If you send two messages with the same `eventId` for the same application, Svix treats the second request as a duplicate and does not deliver it twice.

Use `eventId` whenever you need to guarantee exactly-once delivery from your side — for example, when retrying a failed API call to Svix. Set it to a stable identifier derived from the event itself, such as a database record ID combined with the event type. (needs confirmation)

## Message retention and pruning

Each message has a `payloadRetentionPeriod` that controls how long Svix stores the raw payload. The value is in days and must be between 5 and 90; it defaults to 90.

The server exposes a `prune` CLI command for removing old message data.

After the retention period expires, the payload content is no longer available, but the message record and its delivery attempts remain queryable.

## Broadcast messages

When you send a message to an application, Svix delivers it to every endpoint in that application whose event type and channel filters match. There is no need to address individual endpoints — the fan-out is automatic.

You can also optionally create the application at the same time as the message by including an `application` object in the request body. If the application identified by the path parameter already exists, the `application` field is ignored.
