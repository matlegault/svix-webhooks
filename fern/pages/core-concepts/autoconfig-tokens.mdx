title: "AutoConfig Tokens"
---

AutoConfig tokens let your end-users register webhook endpoints or subscribe to streams without needing direct access to your Svix API credentials.

## What is an AutoConfig token?

When you build a platform on top of Svix, your customers need a way to tell Svix where to deliver their webhooks. Normally that requires an API call on their behalf. AutoConfig tokens solve this by giving you a short-lived, scoped token you can hand to a customer. They use it to configure their own endpoint or stream subscription directly, without ever seeing your main API token. (needs confirmation)

The Svix SDKs expose two classes for working with these tokens: `AutoConfig` (used by the producer — you) and `AutoConfigConsumer` (used by the consumer — your customer). Both are available in Go, Python, TypeScript/JavaScript, Java, Kotlin, and Rust.

## v1 tokens (endpoint-based, deprecated)

v1 tokens have the prefix `auto_v1_`. When a consumer uses a v1 token, it registers a traditional webhook endpoint — a URL that Svix will POST messages to.

v1 tokens are deprecated. You should use v2 tokens for new integrations.

## v2 tokens (subscription-based)

v2 tokens have the prefix `auto_v2_`. They are used with `AutoConfigConsumer` to create a streaming sink subscription rather than a plain endpoint. This is the current recommended approach.

The Go SDK exposes the consumer flow through `NewAutoConfigConsumer(token, sinkIn)`, which takes the token and a sink configuration object.

## Consumer vs. producer flows

There are two sides to AutoConfig:

- **Producer (you):** You call `AutoConfig` to generate a token scoped to a specific application. You then share that token with your customer out-of-band (for example, in your own dashboard or onboarding flow).
- **Consumer (your customer):** They call `AutoConfigConsumer` with the token you gave them and their sink or endpoint details. The SDK handles the API call to register their destination.

In Go, the consumer side looks like this:

```go
consumer := svix.NewAutoConfigConsumer(token, sinkIn)
err := consumer.Subscribe(ctx)
```



In Python, the same split is represented by the `AutoConfig` and `AutoConfigConsumer` classes exported from `svix.api`.

The Java and Kotlin SDKs expose `AutoConfig` and `AutoConfigConsumer` with the same producer/consumer split, supporting both v1 and v2 token formats.

## Token lifecycle and expiry

AutoConfig tokens are short-lived and scoped to a single application. Once a consumer has used a token to register their endpoint or subscription, the token is no longer needed. You should generate a fresh token each time a customer needs to (re)configure their destination.

The model returned when you create a token is `AutoConfigOut`, which is part of the Python SDK's public surface alongside `CreateAutoConfigSubscriptionIn` for v2 subscription creation.

## AutoConfig vs. manual endpoint registration

Without AutoConfig, you register endpoints on behalf of your customers by calling the Endpoint API directly — for example, `POST /api/v1/app/{app_id}/endpoint` — using your own server-side API token.

AutoConfig tokens let you delegate that step to the consumer. The trade-off is:

- **Manual registration** gives you full control over endpoint configuration and keeps all API calls server-side.
- **AutoConfig** reduces the work on your server and lets customers self-serve their own destination setup without exposing your API credentials.

Use AutoConfig when you want to embed a self-service registration flow in your product. Use manual registration when you need to enforce specific endpoint settings or keep configuration entirely under your control. (needs confirmation)
