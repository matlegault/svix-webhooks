---
title: "What is Svix?"
---

Svix is an enterprise-ready webhooks-as-a-service platform that handles webhook delivery, retries, security, and endpoint management so you don't have to build it yourself.

## What Svix is

Svix lets you send webhooks with a single API call. You hand Svix a message, and it takes care of deliverability, retries, signing, and more.

The server is written in Rust and backed by PostgreSQL. It exposes a REST API for managing applications, endpoints, messages, and delivery attempts.

## Core use cases

- **Send webhooks to your customers.** Create an application per customer, register their endpoint URLs, and post messages. Svix queues, signs, and delivers each message with automatic retries.
- **Verify incoming webhooks.** Each SDK ships with a webhook verification helper so your customers can confirm that payloads came from you.
- **Route messages from queues.** Svix Bridge connects Kafka, RabbitMQ, SQS, GCP Pub/Sub, and Redis streams into Svix, so you can feed existing event pipelines into webhook delivery without changing your producers.
- **Subscribe to platform events.** Operational webhooks let you receive notifications about system-level events such as delivery failures.

## Key concepts at a glance

| Concept | What it is |
|---|---|
| **Application** | One logical tenant, typically one per customer. |
| **Endpoint** | A destination URL that belongs to an application. |
| **Message** | The webhook payload you send. |
| **Event type** | A named category for messages, used to filter delivery. |
| **Message attempt** | A single delivery try for a message, with its own status and response. |
| **Idempotency key** | A caller-supplied key that prevents duplicate message sends. |
| **AutoConfig token** | A token that simplifies endpoint registration for your customers. |

## Platform components: server, SDKs, CLI, Bridge

**Server** — The Svix server exposes a REST API at paths such as `POST /api/v1/app`, `POST /api/v1/app/{app_id}/msg`, and `GET /api/v1/app/{app_id}/attempt`. It supports multiple queue backends (Redis, RabbitMQ, in-memory) and cache backends (Redis, memory, none).

**SDKs** — Official client libraries are available for Go, Python, TypeScript/JavaScript, Java, Kotlin, Ruby, C#, Rust, and PHP. Every SDK covers the full API and includes webhook verification.

**CLI** — The `svix-server` binary ships CLI commands for generating JWTs (`jwt generate`), generating asymmetric keys (`asymmetric-key generate`), running migrations, pruning old messages, and wiping an org.

**Bridge** — Svix Bridge routes messages from external queues (Kafka, RabbitMQ, SQS, GCP Pub/Sub, Redis) into Svix, letting you connect existing event pipelines to webhook delivery.

## Self-hosted vs. managed

You can run the Svix server yourself using the Docker image (`svix/svix-server`) or use the managed cloud service at svix.com. The self-hosted server requires PostgreSQL and optionally Redis for queuing and caching.

All API calls authenticate with a JWT passed as `Authorization: Bearer <token>`. The server validates JWTs signed with a configured secret; HS256 is the default, with HS384, HS512, RS256, RS384, RS512, and EdDSA also supported.

## Supported languages and environments

All nine official SDKs support the full API surface and webhook verification:

- Go (module `github.com/svix/svix-webhooks/v2`, requires Go 1.21)
- Python
- TypeScript / JavaScript
- Java
- Kotlin (includes coroutine support)
- Ruby
- C# (.NET)
- Rust
- PHP (requires PHP 8.1 or later)

The code generation templates that produce these SDKs expose helpers such as `messageInRaw()` and `getOrCreate()` across all supported languages.
