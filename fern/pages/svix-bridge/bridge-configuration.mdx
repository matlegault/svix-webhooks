title: "Configuring Bridge"
---

This page is a reference for every configuration key available in Svix Bridge, covering each queue backend, transformation options, and JavaScript engine selection.

## Configuration file format

Bridge is configured through a YAML file. Each entry in the file defines a sender (queue → Svix) or receiver (webhook → queue). You set the backend-specific options directly on the entry alongside optional transformation and output settings.

## Kafka: bootstrap brokers, group ID, topic, SASL, security protocol

Kafka sender inputs use the following keys:

| Key | Required | Description |
|-----|----------|-------------|
| `kafka_bootstrap_brokers` | Yes | Comma-separated list of broker addresses, e.g. `localhost:9094`. |
| `kafka_group_id` | Yes | Consumer group ID used to track stream offset across restarts. |
| `kafka_topic` | Yes | The topic to consume from. |
| `kafka_transformation_input` | No | Input passed to JSON transformations. Values: `payload` (default) or `envelope`. |
| `kafka_auto_offset_reset` | No | Maps to `auto.offset.reset`. Values: `latest` (default) or `earliest`. |
| `kafka_idempotency_namespace` | No | Namespace for idempotency keys from independent Kafka sources. |
| `kafka_security_protocol` | Yes | Security protocol. Values: `plaintext`, `ssl`, `sasl_ssl`. |
| `kafka_debug_contexts` | No | Enables verbose rdkafka logging for the selected contexts. |

For `sasl_ssl`, you also set SASL credentials. The supported `kafka_sasl_mechanism` values are `PLAIN`, `SCRAM-SHA-256`, and `SCRAM-SHA-512`.

Messages are committed manually only after successful webhook delivery — Bridge does not use auto-commit.

Kafka output opts use `kafka_bootstrap_brokers`, `kafka_topic`, `kafka_security_protocol`, and optionally `kafka_debug_contexts`.

## RabbitMQ: URI and queue name

RabbitMQ inputs and outputs are configured with two keys:

| Key | Description |
|-----|-------------|
| `uri` | The AMQP connection URI for your RabbitMQ instance. |
| `queue_name` | The name of the queue to consume from or publish to. |

## Redis: DSN and queue key

Redis inputs and outputs use these keys:

| Key | Description |
|-----|-------------|
| `dsn` | The Redis connection DSN. |
| `queue_key` | The key identifying the queue in Redis. |

Redis only supports JSON-formatted transformations. If you configure a string-format transformation with a Redis backend, Bridge will return an error.

## SQS: queue DSN

SQS inputs and outputs are configured with a single key:

| Key | Description |
|-----|-------------|
| `queue_dsn` | The SQS queue DSN, including region and queue name. |

## GCP Pub/Sub: subscription ID and topic

GCP Pub/Sub inputs and outputs use these keys:

| Key | Description |
|-----|-------------|
| `subscription_id` | The Pub/Sub subscription ID to consume from (input). |
| `topic` | The Pub/Sub topic to publish to (output). |

## Transformation config key and JS engine selection

You can attach an optional `transformation` key to any sender or receiver entry. The transformation contains a JavaScript snippet that Bridge runs on each message before forwarding it.

Bridge supports two JavaScript execution engines: **Deno** and **QuickJS**. You select the engine with the `js_engine` config key. Valid values are `deno`, `quickjs`, or `both`. When you set `both`, Bridge runs the transformation in both engines in parallel, which is useful for validating that your scripts produce consistent results across engines.

String-format transformations work with all queue backends except Redis, which requires JSON-format transformations.

## Webhook receiver and verification

The webhook receiver listens for inbound HTTP POST requests at `POST /webhook/{integration_id}`. Each integration ID maps to a configured verifier and output destination.

You configure verification under the `verification` key of a receiver entry. Two schemes are supported:

- **Svix verification** — set `verification` to `svix` and provide an `endpoint_secret`. Bridge uses the Svix webhook library to validate the signature on each incoming request.
- **No verification** — set `verification` to `none` to accept all incoming requests without signature checking.

A `GET /health` endpoint is also available for liveness checks.
